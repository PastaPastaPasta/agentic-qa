# Prompts

These are the human prompts that drove the Dash Wallet v12 QA run (2026-09-19). Most of the
value came from them. Each one has a reusable template with `<placeholders>`.

## 1. Plan and set up

**Template**

```
Plan out robust QA for <repo/app> based on the below prompt (but use your own guidance /
desires / inspiration of what is needed for good and complete QA). You will need to set up on
this system all that is needed for subagents to run <emulators|simulators|browsers> etc.
<Nothing is set up currently.> LMK if you need sudo for things installed and I can install them.

Once set up, we will do a robust complete QA workflow using opus subagents.

Branch under QA: <branch>
Identify the set of changes since the last major release so we know where to focus QA (do more
QA outside of just that domain too).

Build: <flavour / environment, e.g. testnet>, ideally a release build (any signing key).

Scenarios I care about most:
<numbered step-by-step scenarios with expected results>

Logs: <how the app exports logs>; if that is not available on the device, pull them by other means.
```

**As used**

> Plan out robust QA for dash-wallet based on the below prompt (but use your own guidance / desires / inspiration of what is needed for good and complete QA). You will need to setup on this system all that is needed for subagents to run simulators etc. Nothing is setup currently. LMK if you need sudo for things installed and I can install them.
>
> Once setup; we will do a robust complete QA workflow using opus subagents.
>
> branch on dash-wallet for qa: fix/upgrade-memory-and-sync
>
> we should identify the set of changes since the last major release so we know where to focus QA (do more QA outside of just that domain)
>
> These tests can be done on a testnet build (flavour: _testnet3), ideally with a release build (doesn't matter what keys)
>
> test - start with something simple first: install app / create new wallet, save the recovery phrase / fund it with at 0.11 tDASH / send all balance to shielded / create a non-contested username / save screenshot / More / Security / Reset Wallet / Restore from Recovery Phrase / ensure balance and transactions are same as step 4 after syncing finishes
>
> another test: install app / restore recovery phrase: "<reference seed>" / does the app finish syncing -- last QA testing shows that the sync engine stalled / Balance will be 107.43173749
>
> last test: upgrade from a build from the master branch (version 11.9.0 or higher), build the master branch first, install / restore recovery phrase / wait for syncing to start, it takes an hour or so / install the fix/upgrade-memory-and-sync branch on top, which will trigger the "upgrade" from dashj to the SDK. / does the sync finish? is balance 107.43173749? Does the sync engine stall? are there memory issues?
>
> logs can be generated by going to More / Contact Support … However, if these are not set up on the device, the log files can probably be obtained from the device if it is an emulator by other means.

What it produced: `QA-PLAN.md` (tiers A–E), the environment and helper CLI, signed baseline and
candidate builds, and `AGENT-BRIEF.md`.

## 2. The QA loop (as a `/goal`)

`/goal` installs a Stop hook, so the orchestrator cannot stop until the condition holds. This
one prompt defines the output shape.

**Template**

```
/goal primarily using opus subagents; complete a FULL robust QA loop. Use <funding/fixture
source>; keep most testing to <safe environment>; <optional read-only prod pass>; no real
funds/data. You (via subagents) should QA ALL user stories and ALL changes. Leave no stone
unturned. Collect over time a list of issues, bugs, regressions etc. Take a ton of screenshots
or videos throughout testing. Prepare a final report including a list of all user stories
tested and, by user story, proof (photos or videos) of it either working or failing. Segment
the report so it is easy to go through the issues found and later make fixes. Test with a wide
variety of things: different languages, setups, edge cases, <massive data sets>, etc. You are
one of the final reviewers before shipping this large changeset and it is critical we find all
issues so they can be resolved.
```

**As used**

> primarily using opus subagents; complete a FULL robust QA loop. use faucet.thepasta.org or other sources for tDash; keep most testing to testnet; maybe syncing mainnet; no real funds; You (via subagents) should do a QA over ALL user stories and ALL changes. Leave no stone unturned. Collect over time a list of issues, bugs, regressions etc. You should take a ton of screenshots or videos throughout testing. You should prepare a final report including a list of all user stories tested; and by user story, proof (photos or videos) of it either working, or failing. You should segment the report so that it is easily to go through the issues found and later make fixes. You should test with a wide variety of things; different languages setups; edge cases; massive wallets; etc. You are one of the final reviewers before shipping this large changeset and it is critical we find all issues so they can be resolved.

What it produced: 12 device streams plus a static-review stream, the ledger, the story matrix,
the executive summary, `QA-REPORT.md` and a gallery.

## 3. Publish and polish

Each of these was a short follow-up. Together they are the publishing checklist. Do them
without being asked next time.

| Prompt (as used) | Standing rule |
|---|---|
| "please push the report to github pages for easy viewing etc" | Publish to a public Pages repo and share the URL |
| "since all seeds are testing; just publish them, same for all logs" | Ask about redaction. If everything is throwaway, publish verbatim, including logs |
| "Evidence … are not links / do not pop open" | Every evidence path is a clickable link |
| "some evidence screens are black? is that intended?" | Explain secure-screen black captures on the page and use UI dumps there |
| "sort the DEFECT-LEDGER by severity" | Ledger is severity-sorted |

## 4. Prove the static findings

**As used**

> There are a range of SR based issues; can we please reproduce them in simulator and get logs and prove they are real and update report?

**Template**

```
Take every static-review (code-reading) finding to a device: reproduce it, get logs, prove or
disprove it, and update the report (verdict per item, evidence, severity changes).
```

## 5. Fix loop

**Template**

```
These are the ones to get agents to fix, starting with the ship blockers: <IDs>.
<Context: branch updated / items that may already be fixed / what I'm still seeing>.

For very straightforward fixes have an opus subagent do it. If the fix is more involved have a
<strongest model> subagent do it. Then always have opus subagents perform the interactive
validation and QA on that fix. Deliver an individual PR for each, with the QA artifacts on the
PR. Stack them as needed or put them directly onto the base branch.

Ask questions now if there's anything you need to clarify.
```

**As used**

> These are the ones you can get agents to fix - lets start with the Ship blockers, though there are many more items: D-037, D-041, SR-22, SR-03, SR-04, SR-05, SR-02. Other Items related to sync: SR-01, D-056, D-051 may now be addressed in the updates to this branch, though I am still encountering a stalled sync issue. The branch fix/upgrade-memory-and-sync has been updated.
>
> For very straightforward fixes have a opus subagent do it. If the fix is more involved have a Fable subagent do it. And then always have Opus subagents perform the interactive validation and QA on that fix. For each of the things that I mentioned, you should deliver an individual PR for each of them and you should have the QA artifacts included on that PR. You should have them as stacked PRs as needed or just directly onto the base main branch.
>
> Ask questions now if there's anything you need to clarify.

The orchestrator asked about the PR base, ambiguous IDs, the user's own stall logs, the
artifact form, the PR repo and whether to fix an item that did not reproduce. Answers:
PRs onto the branch under test; artifacts **both** inline in the PR and on a per-PR Pages page;
same-repo PRs; fix the non-reproduced item as hardening. Ask these up front next time.
